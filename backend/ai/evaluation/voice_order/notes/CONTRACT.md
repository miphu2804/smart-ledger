# Build contract — voice-order resolver + eval harness

Frozen interfaces and conventions for the agents building the resolver library
and the offline eval harness. Read `.plans/stt-optimization-plan.md` §5 and §7
alongside this file. **Do not edit this file.** If something here blocks you,
write the blocker in your own notes file and pick the repository-consistent
option.

## Repository facts (verified, do not re-derive)

- Node v22.23.3. There is no bundler in the loop for eval work.
- Run a test from `frontend/mobile`:
  `node --test tests/<name>.test.ts`
- **Relative imports must carry an explicit `.ts` extension**
  (`from './normalizer.ts'`). Node's type stripping needs it; Metro accepts it.
  Precedent in the repo: `frontend/mobile/src/lib/auth/zaloProof.ts`.
- **Data files must be `.ts` modules exporting a plain const, never `.json`.**
  Node requires `with { type: 'json' }` on a JSON import and Metro rejects that
  attribute, so a `.json` import cannot run in both. See
  `src/lib/resolver/phonetic_rules.vi.ts` for the pattern.
- TypeScript is `strict`. `npx tsc --noEmit` from `frontend/mobile` must show no
  new errors.
- No new npm or Python dependency. Everything is pure TypeScript on the standard
  library.
- **No network.** Never fetch anything.

## Eval record schema (all datasets use this)

One JSON object per line, in a `.jsonl` file:

```jsonc
{
  "id": "d2-tap_hoa-0001",     // unique across all datasets
  "dataset": "d1" | "d2" | "d3",
  "catalogId": "tap_hoa",       // key into the catalog registry
  "goldProductId": "103",       // string; null means out-of-catalog (gold NEW)
  "family": "sting-dau",        // near-duplicate family, when the item has one
  "tags": ["loanword"],         // mandatory breakdown tags, see below
  "line": { "rawProductSpan": "nuoc mam nam ngu nam tram ml", "qty": 3, "unit": "chai" },
  "referenceSpan": "nước mắm Nam Ngư 500ml"  // pre-noise span, for error analysis
}
```

Catalog registry: `backend/ai/evaluation/voice_order/data/catalogs.json`, shaped
`{ "<catalogId>": CatalogItem[] }` using the frozen `CatalogItem` type. The three
real catalogs (`tap_hoa` 30, `ca_phe` 20, `quan_com` 18) come from
`backend/ai/evaluation/voice_order/data/prior_catalogs.json`; product ids there are numbers and must be
stringified in the registry.

Tag vocabulary (closed set, use exactly these):
`loanword`, `dialect`, `near_duplicate`, `multi_line`, `out_of_catalog`, `clean`.

Splits: `backend/ai/evaluation/voice_order/data/splits.json`, shaped
`{ "<datasetId>": { "calibration": ["id", ...], "test": ["id", ...] } }`.
Split by **product family** and by **source set** so no family lands on both
sides. Aim for 60/40.

## Retriever contract

Every retriever implements the frozen `Retriever` interface: constructed once
from `(catalog: CatalogItem[], options)`, exposing
`retrieve(line: QueryLine, k: number): RetrievalHit[]` (best first, at most `k`)
and `addDocument(text: string, productId: string): void` for synchronous
incremental indexing.

Rules for all retrievers:

- `retrieve` must be **deterministic**. Ties break by score descending, then by
  `productId` ascending (string compare), so a rerun reproduces the ranking byte
  for byte.
- Never throw on an empty catalog, an empty span, or a span with no match:
  return `[]`.
- Scores are comparable **within** one retriever only. Fusion makes them
  comparable across retrievers.
- Every retriever needs a unit test that pins the plan's hand-computed value
  verbatim, plus tests for the empty/degenerate cases above.

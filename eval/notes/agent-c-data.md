# Agent C — datasets and baselines

Scope: the offline eval harness's **data layer** (`eval/lib/synth.ts`,
`eval/lib/synth_rules.vi.ts`, `eval/lib/d3.ts`, `eval/lib/corpus.ts`,
`eval/lib/baselineR0.ts`) plus the generated artifacts under `eval/data/`.
Nothing outside this list was edited; `parseOrder.ts`, `resolver/**` and the
existing `eval/data/prior_*` files are frozen and untouched.

## What I built

- **`eval/lib/synth_rules.vi.ts`** — the confusion rules as a `.ts` **data
  module** (no logic): the tone inventory, onset/coda confusion groups, foreign
  onsets, the loanword respellings, the size/unit token list, and the start
  weights. Nine rules: `tone_loss`, `tone_swap`, `initial_merge`, `final_merge`,
  `syllable_split`, `syllable_merge`, `loanword`, `truncate`, `char_edit`.
- **`eval/lib/synth.ts`** — the deterministic simulator. `synthesize` rewrites a
  clean span token by token, each rule firing with its own probability from a
  seeded mulberry32 PRNG (`Math.random` is never used). It reports which rules
  fired. `fitWeights(pairs)` fits rule frequencies from observed
  (heard, reference) pairs; `rulesToTags` projects fired rules onto the
  `CONTRACT.md` closed vocabulary.
- **`eval/lib/d3.ts`** — the synthetic stress catalogs (`N ∈ {100, 1000, 5000,
  20000}`), built from `brand × flavour × size`, each item's `family` set to its
  brand slug so every brand is a near-duplicate family. `generateD3Catalog(n,
  seed)` returns the catalog; `buildD3(seed)` returns one lightly-noised eval
  record per item.
- **`eval/lib/corpus.ts`** — the loaders and builders: `loadCatalogs`,
  `buildD1Text`, `buildD2`, `buildSplits`, `writeDatasets`, and the registry
  writer. `writeDatasets` is the one side-effecting function.
- **`eval/lib/baselineR0.ts`** — the R0 adapter that scores the current
  `parseOrder` on the same `QueryLine`s as the resolvers, as a decision.
- **`eval/tests/*.test.ts`** — determinism, weights-as-data, D3 families, split
  isolation, D2 non-empty spans, truncate, and R0's three decisions.
- **`eval/data/`** — `catalogs.json`, `d1.jsonl`, `d2.jsonl`, `d3.jsonl`,
  `splits.json`, `counts.json`, all regenerated by `writeDatasets()`.

## Decisions and why

- **Rules live in a `.ts` data module, not `.json`.** The `CONTRACT.md` rule
  requires it (type stripping and Metro both load `.ts` with no bundler plugin).
  Weights are data: `SYNTH_RULE_NAMES` drives `fitWeights`, and the test
  "rule weights are data" proves that zeroing every weight leaves the input
  unchanged.
- **`truncate` rule added.** Real speakers say "Sting dâu", not "Sting dâu chai
  330ml", and a 20-character catalog name is many edits from an 8-character
  spoken span. Without it D2 only tested small edits to full names. The rule
  drops trailing tokens that read as a size or unit (`chai`, `lon`, `hộp`, `gói`,
  `330ml`, `1kg`, `1 lit`, `lốc 10 cuộn`, …), never the whole span. It carries no
  closed-vocabulary tag; it travels in the record's `rules` field.
- **D1-text spans come from the gold line, not from `parseOrder`.** `parseOrder`
  exposes no per-line product substring (`ParsedOrder` has no `rawProductSpan`),
  so for an in-catalog gold line the span is the matched catalog name, and for a
  non-catalog gold line it is the spoken name `parseOrder` reported (`unknown` /
  `disambiguations` / `missingQuantityItems`). See the limitation below.
- **`buildSplits` splits per independent dataset pool.** D1 and D2 are built from
  the same corpus and share their source sets (`catalog::category`), so they are
  union-found and split as one pool. D3 is independent and split on its own —
  otherwise one 20 000-item catalog, being a single atomic source set, would
  consume the whole global calibration budget. Families are also scoped to their
  catalog: D3 reuses the same brand slug across its four catalogs, so a global
  family key merged every D3 record into one component and collapsed the split
  (`d3 cal=26100 test=0` before the fix).
- **`loadCatalogs` returns the full registry and does not write.** It previously
  returned only the three real catalogs (and wrote `catalogs.json` as a side
  effect of a read), so `runner/run.ts` got three catalogs and every D3 line
  resolved against an empty candidate set. It is now a pure read of
  `buildCatalogRegistry()`; `writeDatasets` owns the write. The name stays
  because `run.ts` imports it.
- **R0 reconstructs a minimal utterance** ("`<qty> <unit> <span>`") because
  `parseOrder` takes a whole utterance, not a `QueryLine`. That is an
  approximation; R0 is compared as a decision (AUTO/ASK/NEW), not on fused
  scores, and every `GateFeatures` field R0 has no notion of is `0` / `null` /
  `'unknown'` under a `// R0 has no gate features` comment.

## Verified

Measured by running the builders and reading the artifacts back (Node v22.23.3,
`node --test` from the repository root). Numbers are measured, not estimated.

**Dataset counts** (`writeDatasets()` return value):

```
{"d1":1087,"d2":1015,"d3":26100,"d1Dropped":0,"d1WithoutMatchedItem":174}
```

**Split sizes** (`eval/data/splits.json`):

```
d1 cal=651 test=436
d2 cal=643 test=372
d3 cal=20000 test=6100
```

D3 is coarse by construction: each stress catalog is one atomic source set, so
it cannot be split across the boundary — `d3_20000` lands in calibration and the
three smaller catalogs in test. D1 and D2 reach ~60/40 because their sources are
finer (`catalog::category`).

**D1-text breakdown:** 1087 records; 1015 with no tag, 41 `out_of_catalog`, 31
`near_duplicate`; 72 records with `goldProductId: null` (41 + 31). By catalog:
`tap_hoa` 424, `ca_phe` 335, `quan_com` 328.

**D2 tags:** 535 with no tag, 302 `clean`, 132 `dialect`, 35 `loanword`, 11
`dialect+loanword`. 713 spans changed from the reference name, 302 unchanged.
Rules that fired most: `char_edit` 184 alone, `tone_loss` 84 alone, `tone_swap`
54 alone, `truncate` 41 alone (plus many combinations).

**D3:** 26 100 records (`d3_20000` 20 000, `d3_5000` 5 000, `d3_1000` 1 000,
`d3_100` 100); all 26 100 carry a `family`; 160 distinct `catalog::family`
keys (4 catalogs × 40 brands).

**D3 recall@3 (after the loader fix).** Via the harness
(`node eval/runner/run.ts --rows R1 --limit 400`) D3 recall@3 is **1.75%** — was
0% before the fix, when every D3 line resolved to an empty candidate set. The
per-catalog picture explains the small number: with a direct E-only resolver,
`d3_100` recall@3 = 1.000 and `d3_1000` = 0.983, but `d3_20000` = 0.000 under
the harness's `eBruteMax` of 500 (and still 0.000 at 5 000 — `RetrieverE`
refuses to brute-force a catalog larger than the cap, so `topK` is empty) and
0.800 uncapped. The harness sample is dominated by `d3_20000`, so the headline
D3 number measures `RetrieverE`'s `eBruteMax` policy against a 20 000-item
catalog, not the data. The D3 spans themselves are light noise of real catalog
names (e.g. `"Number Onẹ hạt chia 240ml"` for `"Number One hạt chia 240ml"`).

**Artifact sizes:** `catalogs.json` 2 917 933 B; `d1.jsonl` 238 970 B;
`d2.jsonl` 250 277 B; `d3.jsonl` 7 797 184 B; `splits.json` 447 264 B.

**Tests:** `node --test eval/tests/synth.test.ts eval/tests/d3.test.ts
eval/tests/corpus.test.ts eval/tests/baselineR0.test.ts` → `# tests 27 / # pass
27 / # fail 0`. This covers determinism (same seed twice → identical), weights
being data, D3 family near-duplicates, splits never leaking a family or a source
set, D2 never emitting an empty span, the `truncate` rule, and R0 hitting all
three decisions.

## Unverified / assumed

- **D1-text spans are exact catalog names — a ceiling, not a result.** Because an
  in-catalog span is the catalog name `parseOrder` matched, the resolver scores
  `top1 = 1.000, FAR = 0` on D1-text. This is a known limitation, recorded here
  so the report can state it plainly. (Measurement reported by the coordinator;
  I did not re-measure it, as the resolver is outside my scope and frozen.)
- **Start weights are unfitted.** No recorded audio or real ASR transcript exists
  in this repository, so the plan's "fit rule frequencies to the D1 error
  distribution" step cannot run. `DEFAULT_SYNTH_WEIGHTS` are documented start
  values; `fitWeights()` is the hook a later phase uses once (heard, reference)
  pairs exist. This is a deviation from plan §7.1.
- **`fitWeights` never detects `truncate`.** `classifyPair` has no way to tell a
  truncation from a deletion, so a fitted `truncate` weight stays 0; only the
  default is non-zero.
- **D1-text is not real ASR data.** It is the written reference transcripts
  segmented by `parseOrder`; there is no audio in the repository.
- **R0's numbers are indicative, not an exact replay**, because of the
  utterance reconstruction above.
- **D3 split is catalog-coarse** (76/24, not 60/40) for the reason given under
  Verified.
- **D3's headline recall is set by `eBruteMax`, not by the data.** `RetrieverE`
  returns no candidates for a catalog larger than its `eBruteMax`, so `d3_20000`
  scores 0 unless the cap is raised above 20 000. That is a harness/config choice
  (see `runner/run.ts`), outside the data layer.

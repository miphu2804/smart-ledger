Why this configuration

The selection rule in eval/configs/selection_rule.json was written and frozen before any of these numbers existed. It excludes every row whose false-auto rate has a 95% confidence interval reaching above 1%, then picks the simplest remaining row within 2 percentage points of the best recall.

Nine of the fourteen rows failed the budget. The highest recall in the whole matrix came from rows that auto-apply far too eagerly, so the rule could not use them.

The pipeline

Each stage below is a real step in frontend/mobile/src/lib/resolver/. The resolver is synchronous and does no I/O, so the app and the offline harness run the same code.

  1. 01

    Normalize the span

    toned() → folded() → spaceRemovedFold()

    Canonical Vietnamese tone placement first, so both written styles of a syllable converge. Then every diacritic is stripped and đ is mapped to d by hand, because NFD leaves it alone. Spaces go last: the index is built on one unbroken string.

  2. 02

    Generate candidates with a count filter

    τ = max(|q|, |d|) − 3 + 1 − 3K  ·  q = 3, K = 2

    The query's padded trigrams are looked up in an inverted index. Each document is kept when it shares at least τ of them with the query. Ukkonen's q-gram lemma lower-bounds edit distance by trigram overlap, so pruning at that bound cannot discard a document within edit distance 2. Posting lists are walked and counted, never intersected.

  3. 03

    Score with IDF-weighted cosine

    idf(t) = ln((N − df + 0.5) / (df + 0.5) + 1)

    Cosine between the query's and the document's trigram term-frequency vectors, each term weighted by its inverse document frequency. Rare trigrams carry the decision; the ones every catalog name shares carry almost nothing. Scores land in [0, 1], which the gate's floor depends on.

  4. 04

    Fuse and cut to five

    F1 max · raw score, no max-normalize

    With one retriever, fusion is a pass-through. The variant matters anyway: max-normalizing would force every query's top hit to exactly 1, which makes the score constant and puts the gate's floor out of reach, so an unmatched line would look as confident as a perfect one.

  5. 05

    Decide: answer, ask, or offer a new item

    AUTO · ASK · NEW

    The gate reads the fused score, the margin to the runner-up, the dispersion of the candidate scores, inter-retriever agreement, unit agreement, alias trust and query length. The rule chain is the next section.

  6. 06

    Learn from the correction

    upsertAlias() · trusted at 2 confirmations

    When the shop corrects an ASK, the corrected phrase is recorded and indexed as an extra document on first sight, so the next utterance that sounds like it reaches the right product without a rebuild. Re-confirming does not add the document again, which would skew document frequencies.

The gate, in order

The order is load-bearing. An alias hit auto-applies even at a low score, and a low score becomes NEW before anything else is considered. Thresholds are tuned on the calibration split only, against a 1% false-auto budget.

  • A trusted alias resolves to the top-1 product → AUTO

  • s1 < sFloor → NEW  sFloor = 0.587

  • s1 ≥ sAuto and margin ≥ mMin and agree = 1 and unit_ok ≠ mismatch → AUTO  sAuto = 1.0, mMin = 0

  • otherwise → ASK

The thresholds come from the calibration split's own score distribution, not a fixed 0 to 1 ladder. An earlier fixed ladder could never be cleared by an RRF score, which lives near 0.016, and every such row silently auto-applied nothing.

Why candidate generation runs before edit distance

Above 500 catalog items, the edit-distance and phonetic retrievers score only the ids the trigram index hands them. This is the plan's argument for Q-before-E, and it is measured rather than assumed.

Where it is weak

Recall splits sharply by noise type. On clean written spans the resolver is at the ceiling. On dialect-confused spans it drops to 70.9%, and on names that differ from a catalog row only by a word or two it finds nothing at all, because a near duplicate is exactly where a character-trigram score cannot separate two candidates.

D3 carries the discrimination: 88.6% recall@3 over catalogs from 100 to 20,000 items, with a 0.3% false-auto rate. D1 is a ceiling rather than a result, because an in-catalog D1 span is the catalog name the segmenter matched.

The gain is in ranking, not in the confidence of the autos.

What these numbers do not support

D1 is written reference transcripts, not recorded audio. No audio exists in this repository, so the whole STT axis of the plan, greedy against beam search, hotwords, silence padding, could not be run. The D2 confusion weights are start values rather than weights fitted to real ASR output.

No device latency was measured, and the Qdrant Edge parity oracle has no implementation, because the harness is pure TypeScript with no new dependencies by design. Neither result should be read as a production claim.

Findings this rests on

Five defects were found only when the three independently built parts were joined. Each one produced a plausible number rather than a crash, so each is worth knowing about before reading any single figure above.

  • The edit-distance and phonetic retrievers scored nothing above the brute-force cap in any configuration without Q. The candidate provider was injected unconditionally and returned an empty list when no Q retriever existed. Every E-only row in an earlier run looked like a weak retriever when it had in fact searched nothing. Fixed in index.ts and guarded by two tests.

  • The catalog loader returned only the three real catalogs. All 26,100 D3 lines resolved against an empty catalog. The giveaway was that a brute-force retriever also found nothing. Symptom as first measured: D1 100%, D2 100%, D3 0%.

  • Sampling pooled every dataset together. D3 is 26,100 of 28,202 records, so a 40-line sample was 35 D3 lines, and the headline described D3 while looking like it described the corpus. Replaced with a per-dataset sample.

  • The gate tuner learned to answer NEW to everything. Neither tuner counted a NEW as a cost, so raising the floor above every candidate satisfied the budget perfectly. R4, R5 and R6 all reported FAR 0.0% with zero autos, and the rule picked a configuration that resolved nothing. In that run NEW precision was 4.2%, so almost none of those NEW decisions were actually out of catalog. The objective is now the non-auto rate, which makes that gate score worst instead of best.

  • The threshold grid assumed one score scale. A raw similarity lives in 0 to 1, an RRF score near 0.016, and the grid's lowest auto threshold was 0.3, so no RRF score could clear it. Candidate thresholds now come from the calibration split's own feature distribution, and the fallback flipped from NEW-everything to ask-everything.
